工作流是可复用资产，Session 是一次开发记录

定义导出帮助复用流程；Session 导出帮助复查一次开发。二者不能混为一份“完整环境备份”。

JSON / YAML / Markdown 如何进入同一份定义

parse_document 只解析数据，不执行代码。文件必须是非空 UTF-8 文本，最大 100 KB。Markdown 必须包含一个完整的工作流代码块；JSON 拒绝重复字段，YAML 使用安全 Loader，拒绝自定义对象、重复 / 非字符串字段与锚点引用。

导入先做 Schema 校验，再分配新的 Workflow ID 和 revision 0，形成未保存草稿；名称冲突时给出建议，最终保存仍在文件锁内检查。import 本身不自动执行开发，也不覆盖同名流程。

可移植的双工具工作流 
schema: 1
id: code-review-demo
name: 编码与独立审查
revision: 0
steps:
  - id: code
    name: 实现与自测
    tool: claude
    model: auto
    effort: ""
    prompt: 根据需求实现功能，运行测试并保存真实 diff。
  - id: review
    name: 安全与测试审查
    tool: codex
    model: auto
    effort: ""
    prompt: 读取真实 diff，执行适用测试，报告问题与验证范围。

这份示例没有硬编码账号专属模型。auto 不表示两个工具使用相同模型，也不保证目标工具已经登录。

“根据意图生成”不是把固定模板伪装成 AI 结果

{{diagram:generate}}

生成入口有独立 request_id 与独立 Chat slot；同一请求 ID 对应不同意图时拒绝。后台向现有 poc-kiro 发送纯文本设计任务，请它返回一个完整 JSON 代码块，不读取项目、不执行开发、不派生子任务。

工作台读取原生回复，经过解析、结构与参数校验后，提供“采用草稿”。无效回复显示真实错误，不悄悄替换成固定模板。生成需要权限时，用户进入原生生成对话处理。生成结果在采用、编辑和显式保存之前，不进入开发运行。

操作当前实现不会自动发生的动作
单个 / 批量导出选择 1–20 个 Session，校验后打包原生 Layer A 与运行证据不会主动请求工具私有 Layer B

Session 导出包含什么

文件内容

workflow.yaml / workflow.md本次固定配置版本
report.json / conversation.md观察报告与原生导出所含对话

为什么当前没有直接引入 SQLite

已验证规模下，文件锁、原子替换和版本快照能支撑需求；额外数据库会引入迁移和双份权威数据问题。需要跨多项元数据事务、持久调度租约或多用户写入时，再建立明确的数据库层。

归档不是备份，导出 ZIP 也不包含完整代码工作目录、所有工具私有上下文或认证。迁移需单独保留运行目录、原生 Crew 数据及被允许保留的工具状态，并验证一致性与恢复。没有做过恢复演练，就不应承诺“记忆永不丢失”。

HTTP 与 MCP 分工

主机侧 HTTP 负责创建 slot、附加 context、发送 chat、读取状态和原生导出。工作台自己的 HTTP 负责配置和展示。真正的子 Agent 分派来自父对话调用原生 MCP spawn_run。因此“有一个 HTTP 工作台”不等于“又实现了一个调用模型的调度服务器”。

当前模块保留 PoC 命名和较集中的 workflow.py；将来拆分服务时，应先保持参数和数据契约，再按职责拆模块。不要在同一轮同时更改接口、存储和恢复语义，否则很难判断问题来自哪里。

用一份小型需求，走完整条证据链

推荐演示一个零依赖的本地 Web 应用：发布说明工作台，支持分类、实时预览和 Markdown 导出。它足够小，能把讨论集中在多工具协作与交接上。

做一个蓝白色的发布说明工作台，支持按功能、修复和优化分类，实时预览并导出 Markdown。使用本地 HTML / CSS / JavaScript，无需安装依赖。

操作顺序与每一步应展示的证据

  1. 打开工作台，选择四工具模板。

    在任务页展示每步的职责、工具、模型与 Effort。首次跨环境验证优先用 auto，之后再验证明确模型。

  2. 输入需求，确认后开始。

    展示 Run ID、固定 revision 和 App 父对话。说明无需用户手写 Plan / Tasks。

  3. Kiro 规划。

    查看真实规划文件、验收标准与 handoff；展示原生工具身份，而不是只展示回答里的角色名。

  4. Claude 编码。

    打开实际代码和 candidate.diff，运行适用测试，保留真实退出结果。原生执行结束后，再查看交接核对。

  5. Codex 审查。

    让它读取同一候选的 diff 和文件，核对安全 / 测试范围；有 BLOCKED 就停止。未运行的测试必须明确说明。

  6. OpenCode 整理交付。

    生成本地前端与使用说明。检查是否修改了已审查核心；发生修改时不能继续沿用旧 Review 作为完整证明。

  7. 回到报告，完成导出。

    展示每步 Task / 工具 Session、请求与实际模型、Effort 证据、交接与产物。导出 Session 开发手册和 Release 候选。

原生环境与只读报告的区别

本报告可直接离线打开。要实际运行 MVP，需要已初始化的 KiroCrew 0.7.1 / 0.7.2、现有 macOS 启动环境，以及分别安装和登录的 Coding 工具。运行 Workflow Studio.command 或对应 Python 启动器，工作台默认使用 8917，Gateway 使用 5476。

启动器不会强制终止不属于自己的 Gateway。若当前 Gateway 尚未加载桥接更新，只在聊天、子任务、队列和权限请求都空闲时优雅重载；忙碌时保留工作。这个启动行为不是 EC2 无桌面部署方案。
