Registry 的封装顺序

  1. 准备多个配置副本。每个后端获得独立的配置副本，把 acp_backend 和 member backend 设到目标路径，再调用已有 create_provider_factory()。
  2. 保留普通 Agent 行为。不属于专用 poc-* 模板的请求交给原 Registry；未知的 poc-* 名称会明确报错。
  3. 按模板选择 factory。poc-claude 进入 Claude factory，poc-codex 进入 Codex factory。Agent 模板的工具策略与后端选路分别承担职责。
  4. 检查实际 Provider。创建后读取 provider.client.backend，与期望后端比较，再记录路由证据。Agent 自称“我是 Codex”不构成身份核验。

ACP 提供共同的会话协议，但不抹平每个工具的差异。会话恢复、模型配置、工具权限、文件操作和用量返回都要按后端实际能力处理。最细的路由粒度是一次子任务 / 子 Session，并不是每次 read、write 或 shell 调用都更换 Coding Agent。

为什么关闭 session sharing 与 warm pool？

当前 Registry 要求 session_sharing=false、pool_size=0，避免跨后端误复用已有工具会话。复用的是 Provider 接口与管理机制，不是把四个工具强行塞进同一个活跃 ACP 连接。

第三方 Provider 与 MCP 应放在哪里

模型服务由选中的 Coding Tool 自己访问。能否使用第三方平台，要看该工具和适配器对 endpoint、认证和模型的实际支持；本 MVP 没有统一转发所有模型请求的服务。外部 MCP 也按工具配置、Crew 投射和权限进入，不会因为电脑上装过某个 MCP 就对全部后端自动可用。

07

配置请求、原生请求、实际生效，是三层证据

用户选择具体模型，意味着执行约定被固定。即使任务生成了正确代码，也不能用“测试通过”替代“实际工具和模型符合配置”的检查。

模型候选从哪里来

provider_models.json 中的命名空间按工具区分：Kiro 对应 acp，Claude 对应 claude_code，其余读取各自命名空间。“刷新候选”是重新读取本机缓存，不等同于向云端实时验证账号权限。

Claude 的明确模型在 prepare、submit 和每次 next 前检查是否已被该工具公布。候选未出现时停止；已保存的可移植定义和旧快照不因此被改写。Codex 当前候选还会补入本 PoC 观察过的模型，完整动态目录与逐模型 Effort 筛选尚未全部接通。

候选被公布也不是权限保证：组织策略、服务端拒绝或工具降级仍可能改变实际模型，所以执行后还要核对。auto/default 表示允许后端选择模型；当前 Schema 不允许它们搭配非空 Effort。

{{diagram:model}}

Codex 为什么需要内部组合 ID

本机联调发现，裸模型 ID 与默认 Effort 的解析可能让本次覆盖失效；但原生公开 spawn_run Schema 又拒绝含方括号的模型 ID。因此，公开配置保持 model / effort 分开，参数验证后在 Registry 内部生成 model[effort]，再由原生 ACP 逻辑拆分设置。这是版本兼容桥接，不是新协议。

观察器还可以按工具 Session 读取 Codex 的 turn_context 元数据作为直接证据。无法取得时保留来源和未知状态，不能用模型在回答中自报的 Effort 代替。

08

共享的是任务证据，不是四个模型的私有记忆

新加入一个 Agent，不会自动知道前面所有对话。MVP 通过明确的文件路径、前置结果和同一运行目录，让下游重新读取本次任务需要的上下文。

{{diagram:context}}

完整信息怎样越过 5,000 字符限制

原生 spawn_run.task 长度上限是 5,000 字符。next_step 把完整用户需求、本步任务和前置结果路径写进 <step>-instructions.md；分派文本只带摘要、完整指令路径与 REQUEST.md 路径。

完整原生返回保存为 <step>-result.txt，前序 handoff 文件也以路径进入下一步。这样没有把超长内容直接截断成唯一依据，但仍需要 Agent 实际读取文件。文件是否完整、路径是否正确、说明是否遗漏，仍影响执行质量。

优势

可追溯、可复查

文件、返回和收据保留在 Run 下，可以重新读取，不依赖一个不断增长的聊天窗口。

成本

重新读取与重复理解

不同工具分别消耗 Token 理解资料，没有跨工具 KV Cache。长文件、重复描述与错误交接仍会降低效率。

边界

不是永久保活

keep=true 仍受原生保留策略约束；证据包不是全部私有会话状态的备份。

Memory 在本 MVP 中的角色

子任务固定 include_memory=false，避免无关长期记忆干扰明确的演示任务。KiroCrew 原有 Memory 和历史 Sessions 保留；其他原生项目 / 教训上下文仍按 KiroCrew 自己的默认处理。这里没有实现团队共享 Memory，也不能从“跨工具读文件”推导出长期记忆会自动同步。

同工具续作如何保存身份

{{diagram:continue}}

spawn_continue 可以在同一工具 Conversation 中补齐交付，但会生成新 Task ID。观察器从父 App 的原生回执确认新任务与 Conversation 的关系，再核对持久化的 Crew Session 归属。旧接受记录保存在 accepted/previous/，新任务仍要通过全部交接条件；空返回 _No response._ 不被接受。

accept 接受的是可核查的交接

“任务执行结束”只是条件之一。当前实现还会核对观察快照、归属、Agent、后端、参数、原生回执、BLOCKED 标记和交接文件。

{{diagram:handoff}}
检查层具体条件失败时的含义
观察有效connected 为真，快照年龄在 0–20 秒内证据不足 / 过期，不能凭旧页面认定成功

阻塞与交接原生结果不含规定格式的 BLOCKED；handoff 文件存在且非空缺少可供下一步使用的实际交接

通过后，系统保存原生返回、路由、模型与 Effort 证据，以及 handoff 的 SHA-256，写入 accepted/<step>.json。不通过则写入 checks/<task-id>.json，保留错误原因，而不是抹去原任务结果。

当前没有完成“候选代码与安全审查”的自动绑定

收据哈希的是 handoff 文件，不是所有代码、测试与 review 的联合快照。它不能自动证明 Codex 审查的候选与 OpenCode 最终交付完全一致，也不能把非空 handoff 当成安全 PASS。

客户演示时怎样准确说明质量

先展示实际 candidate.diff 和测试退出结果，再展示 Review 结论及其检查范围。最后确认交付阶段有没有修改已审查核心。若候选变更，旧 Review 对新候选可能失效，需要重新验证。把候选哈希、审查结论和写回绑定，是下一阶段明确的增强项。

工作者报告 BLOCKED 时停止，缺失测试时标明未运行。当前没有通用自动重试、任意分支、并行或强制质量门禁；图中的绿色“已交接”不能自动解释成“生产可发布”。

整体进度 = 已接受交接的任务数 ÷ 总任务数。一个长时间运行的编码任务不会靠动画把百分比慢慢填满。

观察器把哪些证据放在一起

  • 原生任务与权限：读取 /api/spawn、/api/approvals，得到实际状态与待处理请求。
  • 父 App 工具回执：从本 Run 的原生记录关联 spawn_run / spawn_continue、Task ID、参数和 Conversation。
  • Factory 路由：provider-routing.jsonl 记录实际 Provider 后端，不依赖模型自述。
  • 工具 / Crew 元数据：查找请求模型、解析模型、可用的 Effort 观察值，以及工具 Session。
  • 交接与检查文件：已接受、未通过和缺失证据按 Run 关联，形成 live / report 投影。

实际 UI 在断连、快照超过 15 秒或系统要求减少动态效果时停止运行段动画。accept 的有效快照阈值是 20 秒，两者目的不同：前者避免视觉上假装实时，后者决定能否使用观察证据验收。

Session 归档不意味着任务停止；关闭浏览器也不意味着原生执行被取消。界面应显示真实执行状态，而不是把 UI 生命周期当作任务生命周期。

看得见“证据来源”，才便于排查问题

一个有效报告应同时保留配置值、原生请求、实际观察、任务身份和错误原因。dispatch-*.json 只是期望参数文件，本身不证明调用已经发生。

11

进入原生对话时，认证由原生机制完成

普通 /chat?sid=... 链接只指定对话，不携带登录状态。工作台提供独立入口，在主机侧取得本次登录地址，再由 KiroCrew 建立浏览器 Session。

{{diagram:auth}}

为什么不会要求用户复制 Token

crew-entry 先以 run ID 调用同源 /api/app-entry。服务端验证 Host、Origin、自定义请求头和 Run，绑定到快照中确定的父 Session。主机侧使用已有 .local_secret 请求原生 Token，登录地址只返回给本次入口响应。

工作台不把 Token 存进配置、Run 快照、静态 HTML、自己的 localStorage 或报告。原生机制处理 HttpOnly Cookie；文档记录的链接交换窗口最长 5 分钟，申请的浏览器 Session 生命周期是 8 小时。这两种时间不应混为一谈。

{{diagram:boundaries}}

配置页与交付预览为什么使用不同主机名

工作台在 127.0.0.1:8917，交付预览在 localhost:8917。它们是不同浏览器 Origin；服务端对配置修改要求明确 Host / Origin / Header，预览路由另外限制路径、文件类型和 CSP。预览内容不能直接使用工作台修改接口。

这保护的是当前可信本机场景中的入口边界，不是完整的多用户隔离。owner Token 不代表每个团队成员各自的权限；未来 Enterprise 还需要服务端项目授权、隔离 Worker 与审计。

工具权限仍回到 KiroCrew 处理

父子任务的权限请求沿原生链路返回。客户演示应打开 KiroCrew 查看实际请求、操作范围和结果，不需要自己手写 MCP 配置，也不应为了“演示流畅”把所有工具设置成无条件允许。

OpenCode 的当前集成曾出现 fs/write_text_file 方法不兼容，阶段指令会使用其已有 Shell 配合 Python / Node 完成文件操作。这条兼容路径仍须获得原生权限；Shell 被拒绝就停止，不增加自定义 RPC，也不绕过权限。
