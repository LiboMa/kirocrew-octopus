01

先看清这个 MVP 做了什么

把它理解成一份可执行的“开发任务书”：每一项工作指定谁来做、用什么模型、交接什么结果；KiroCrew 负责把任务送到实际 Coding Agent，工作台把证据收回来。

需求由用户输入，计划、测试和任务产物由工作者按步骤生成。工作流配置负责角色与约定，实际工程内容在运行目录中产生。

可靠无人值守调度、团队权限、隔离 Worker、仓库 Connector。EC2 目前只保留设计，先完成本地基础测试。

客户获得的是基于已有 KiroCrew 扩展接口交付的框架。它既不要求客户重新编写 ACP Adapter，也不能描述为“只安装未经扩展的原版 App，写一个 JSON 就自动出现这些界面”。

02

配置层决定约定，原生层负责执行

系统中有两条同时存在的路径：向下是“准备需求 → 原生分派 → 工具执行”；向上是“真实事件 → 观察与核对 → 页面显示”。进度页面的刷新不负责推进 Agent。

四个关键边界

  1. 输入边界。Web、配置文件和 Chat 最终都通过同一套结构校验、保存和版本规则。后台轮询不会替用户保存草稿。
  2. 调度边界。workflow.py next 输出精确参数。父 Agent 经原生 MCP 调用 spawn_run，而不是网页自己调用 Coding CLI。
  3. 路由边界。PocProviderRegistry.create_factory 将专用 Agent 模板映射到原生 ACP factory，保留 KiroCrew 的会话与权限流程。
  4. 证据边界。发送配置、拿到 Task ID、工具返回结果、接受交接，是不同阶段。看板必须说明每个判断来自什么证据。
ACP 和 MCP 在这里各做一件事

MCP 是父 Agent 使用 spawn_run 等工具的通道。ACP 是 KiroCrew 驱动目标 Coding Agent 会话的协议。外部 MCP Server 还可以成为目标工具可用的能力，但它不是 ACP 后端本身。

为什么不直接使用上游 Workflow DSL？

基线文档记录的本机版本中，原生 Workflow DSL 的 ctx.agent(effort=...) 没有在对应执行路径完整下传到 SessionManager。MVP 因而沿用已验证的 App → SubagentManager → spawn_run 参数链。这个选择针对当时版本，不能推导为上游永远不支持。

Octopus 的 JSON 定义、保存目录与上游原生 /workflow 库也不是同一个存储。报告会使用“Octopus Workflow”描述这里的定义，避免把两套产品能力混在一起。

定义可以变化，本次运行的约定不能偷偷变化

Workflow 是可复用定义；revision 是一次有效保存；Run 是带有固定版本和原始需求的一次开发；每个步骤又关联一次或多次原生执行尝试。

保存时，有三道明确约束

  1. 结构校验：只接受约定字段；步骤 ID、工具、模型和 Effort 必须满足约束。
  2. 同一写入锁：文件、Web、Chat 的保存进入相同文件锁。名称经过 NFKC、空白归一和 casefold 比较，不允许不可见控制字符。
  3. 乐观版本检查：expected_revision 必须等于当前版本。冲突时要求重新加载、合并，不静默覆盖。内容没有变化时返回已有版本，不无意义递增。

版本实际文件名是零填充序号，例如 state/workflow-versions/<id>/000001.json；文档中 r1、r2 是便于阅读的简称。新 Run 保存完整定义与 SHA-256，之后通过快照核对读取。

    ACP 提供共同的会话协议，但不抹平每个工具的差异。会话恢复、模型配置、工具权限、文件操作和用量返回都要按后端实际能力处理。最细的路由粒度是一次子任务 / 子 Session，并不是每次 read、write 或 shell 调用都更换 Coding Agent。

    为什么关闭 session sharing 与 warm pool？

    当前 Registry 要求 session_sharing=false、pool_size=0，避免跨后端误复用已有工具会话。复用的是 Provider 接口与管理机制，不是把四个工具强行塞进同一个活跃 ACP 连接。

    第三方 Provider 与 MCP 应放在哪里

    模型服务由选中的 Coding Tool 自己访问。能否使用第三方平台，要看该工具和适配器对 endpoint、认证和模型的实际支持；本 MVP 没有统一转发所有模型请求的服务。外部 MCP 也按工具配置、Crew 投射和权限进入，不会因为电脑上装过某个 MCP 就对全部后端自动可用。

    用户选择具体模型，意味着执行约定被固定。即使任务生成了正确代码，也不能用“测试通过”替代“实际工具和模型符合配置”的检查。

    模型候选从哪里来

    provider_models.json 中的命名空间按工具区分：Kiro 对应 acp，Claude 对应 claude_code，其余读取各自命名空间。“刷新候选”是重新读取本机缓存，不等同于向云端实时验证账号权限。

    Claude 的明确模型在 prepare、submit 和每次 next 前检查是否已被该工具公布。候选未出现时停止；已保存的可移植定义和旧快照不因此被改写。Codex 当前候选还会补入本 PoC 观察过的模型，完整动态目录与逐模型 Effort 筛选尚未全部接通。

    候选被公布也不是权限保证：组织策略、服务端拒绝或工具降级仍可能改变实际模型，所以执行后还要核对。auto/default 表示允许后端选择模型；当前 Schema 不允许它们搭配非空 Effort。

    Codex 为什么需要内部组合 ID

    本机联调发现，裸模型 ID 与默认 Effort 的解析可能让本次覆盖失效；但原生公开 spawn_run Schema 又拒绝含方括号的模型 ID。因此，公开配置保持 model / effort 分开，参数验证后在 Registry 内部生成 model[effort]，再由原生 ACP 逻辑拆分设置。这是版本兼容桥接，不是新协议。

    观察器还可以按工具 Session 读取 Codex 的 turn_context 元数据作为直接证据。无法取得时保留来源和未知状态，不能用模型在回答中自报的 Effort 代替。

    08

    共享的是任务证据，不是四个模型的私有记忆

    新加入一个 Agent，不会自动知道前面所有对话。MVP 通过明确的文件路径、前置结果和同一运行目录，让下游重新读取本次任务需要的上下文。

    完整信息怎样越过 5,000 字符限制

    原生 spawn_run.task 长度上限是 5,000 字符。next_step 把完整用户需求、本步任务和前置结果路径写进 <step>-instructions.md；分派文本只带摘要、完整指令路径与 REQUEST.md 路径。

    完整原生返回保存为 <step>-result.txt，前序 handoff 文件也以路径进入下一步。这样没有把超长内容直接截断成唯一依据，但仍需要 Agent 实际读取文件。文件是否完整、路径是否正确、说明是否遗漏，仍影响执行质量。

    优势

    可追溯、可复查

    文件、返回和收据保留在 Run 下，可以重新读取，不依赖一个不断增长的聊天窗口。

    成本

    重新读取与重复理解

    不同工具分别消耗 Token 理解资料，没有跨工具 KV Cache。长文件、重复描述与错误交接仍会降低效率。

    边界

    不是永久保活

    keep=true 仍受原生保留策略约束；证据包不是全部私有会话状态的备份。

    Memory 在本 MVP 中的角色

    子任务固定 include_memory=false，避免无关长期记忆干扰明确的演示任务。KiroCrew 原有 Memory 和历史 Sessions 保留；其他原生项目 / 教训上下文仍按 KiroCrew 自己的默认处理。这里没有实现团队共享 Memory，也不能从“跨工具读文件”推导出长期记忆会自动同步。

    同工具续作如何保存身份

    spawn_continue 可以在同一工具 Conversation 中补齐交付，但会生成新 Task ID。观察器从父 App 的原生回执确认新任务与 Conversation 的关系，再核对持久化的 Crew Session 归属。旧接受记录保存在 accepted/previous/，新任务仍要通过全部交接条件；空返回 _No response._ 不被接受。

    已安装的 Tools、Skills 和 MCP 能被加载吗？

    层次基线中已核对的加载机制需要观察什么
    Claude适配器启用 user / project / local settingSources，结合本次 cwd项目规则是否在当前工作区，权限和依赖是否可用
    Codex原生 App Server，按 cwd 刷新 skills/list发现技能不等于已经读取或执行它
    KiroAgent resources 的 skill:// 映射与 Crew 受管理技能发现当前 poc-* 的空 resources 不能理解成“加载全部技能”
    MCPCrew 投射和工具自己的配置分别生效服务名、认证、权限与后端支持；模板空 mcpServers 不等于原生工具所有 MCP 都关闭

    原业务仓库的技能不会因为“在同一台机器”就自动进入本次独立 workspace。正确证据顺序是已发现 → 已读取 / 注入 → 实际执行。本报告承接基线源码核对，不声称已触发并测试本机全部技能。

    09

    accept 接受的是可核查的交接

    “任务执行结束”只是条件之一。当前实现还会核对观察快照、归属、Agent、后端、参数、原生回执、BLOCKED 标记和交接文件。

    检查层具体条件失败时的含义
    观察有效connected 为真，快照年龄在 0–20 秒内证据不足 / 过期，不能凭旧页面认定成功
    任务身份当前步骤、task-id、parent、Agent 对应防止拿另一条对话或前次任务的结果验收
    执行结果done 且没有 error / stopped；结果非空区分失败、取消、未结束或空响应
    后端与参数actual_backend、请求模型、实际模型、原生 Effort 请求对应任务可以已经返回，但执行约定未满足
    续作新回执的 Conversation 对应 Crew Session不能只凭新 Task ID 就声称复用了正确会话
    阻塞与交接原生结果不含规定格式的 BLOCKED；handoff 文件存在且非空缺少可供下一步使用的实际交接

    通过后，系统保存原生返回、路由、模型与 Effort 证据，以及 handoff 的 SHA-256，写入 accepted/<step>.json。不通过则写入 checks/<task-id>.json，保留错误原因，而不是抹去原任务结果。

    当前没有完成“候选代码与安全审查”的自动绑定

    收据哈希的是 handoff 文件，不是所有代码、测试与 review 的联合快照。它不能自动证明 Codex 审查的候选与 OpenCode 最终交付完全一致，也不能把非空 handoff 当成安全 PASS。

    客户演示时怎样准确说明质量

    先展示实际 candidate.diff 和测试退出结果，再展示 Review 结论及其检查范围。最后确认交付阶段有没有修改已审查核心。若候选变更，旧 Review 对新候选可能失效，需要重新验证。把候选哈希、审查结论和写回绑定，是下一阶段明确的增强项。

    工作者报告 BLOCKED 时停止，缺失测试时标明未运行。当前没有通用自动重试、任意分支、并行或强制质量门禁；图中的绿色“已交接”不能自动解释成“生产可发布”。

    11

    进入原生对话时，认证由原生机制完成

    普通 /chat?sid=... 链接只指定对话，不携带登录状态。工作台提供独立入口，在主机侧取得本次登录地址，再由 KiroCrew 建立浏览器 Session。

    为什么不会要求用户复制 Token

    crew-entry 先以 run ID 调用同源 /api/app-entry。服务端验证 Host、Origin、自定义请求头和 Run，绑定到快照中确定的父 Session。主机侧使用已有 .local_secret 请求原生 Token，登录地址只返回给本次入口响应。

    工作台不把 Token 存进配置、Run 快照、静态 HTML、自己的 localStorage 或报告。原生机制处理 HttpOnly Cookie；文档记录的链接交换窗口最长 5 分钟，申请的浏览器 Session 生命周期是 8 小时。这两种时间不应混为一谈。

    配置页与交付预览为什么使用不同主机名

    工作台在 127.0.0.1:8917，交付预览在 localhost:8917。它们是不同浏览器 Origin；服务端对配置修改要求明确 Host / Origin / Header，预览路由另外限制路径、文件类型和 CSP。预览内容不能直接使用工作台修改接口。

    这保护的是当前可信本机场景中的入口边界，不是完整的多用户隔离。owner Token 不代表每个团队成员各自的权限；未来 Enterprise 还需要服务端项目授权、隔离 Worker 与审计。

    工具权限仍回到 KiroCrew 处理

    父子任务的权限请求沿原生链路返回。客户演示应打开 KiroCrew 查看实际请求、操作范围和结果，不需要自己手写 MCP 配置，也不应为了“演示流畅”把所有工具设置成无条件允许。

    OpenCode 的当前集成曾出现 fs/write_text_file 方法不兼容，阶段指令会使用其已有 Shell 配合 Python / Node 完成文件操作。这条兼容路径仍须获得原生权限；Shell 被拒绝就停止，不增加自定义 RPC，也不绕过权限。

    12

    工作流是可复用资产，Session 是一次开发记录

    定义导出帮助复用流程；Session 导出帮助复查一次开发。二者不能混为一份“完整环境备份”。

    JSON / YAML / Markdown 如何进入同一份定义

    parse_document 只解析数据，不执行代码。文件必须是非空 UTF-8 文本，最大 100 KB。Markdown 必须包含一个完整的工作流代码块；JSON 拒绝重复字段，YAML 使用安全 Loader，拒绝自定义对象、重复 / 非字符串字段与锚点引用。

    导入先做 Schema 校验，再分配新的 Workflow ID 和 revision 0，形成未保存草稿；名称冲突时给出建议，最终保存仍在文件锁内检查。import 本身不自动执行开发，也不覆盖同名流程。

    “根据意图生成”不是把固定模板伪装成 AI 结果

    生成入口有独立 request_id 与独立 Chat slot；同一请求 ID 对应不同意图时拒绝。后台向现有 poc-kiro 发送纯文本设计任务，请它返回一个完整 JSON 代码块，不读取项目、不执行开发、不派生子任务。

    工作台读取原生回复，经过解析、结构与参数校验后，提供“采用草稿”。无效回复显示真实错误，不悄悄替换成固定模板。生成需要权限时，用户进入原生生成对话处理。生成结果在采用、编辑和显式保存之前，不进入开发运行。

    采用后回到目标页：项目 / 工作流名称使用生成的 config.name 并处理重名，本次开发目标使用该生成请求提交的完整意图。等待期间改写输入框不会替换已提交意图。用户采用后可以继续编辑，轮询与旧 Session 的刷新不会覆盖新草稿；最终确认后才通过已有开始接口发送目标。

    Session 管理保留历史

    操作当前实现不会自动发生的动作
    单个 / 批量导出选择 1–20 个 Session，校验后打包原生 Layer A 与运行证据不会主动请求工具私有 Layer B
    Session 归档 / 恢复写工作台 session-meta 标记，改变列表可见性不停止原生任务、不删除对话

    HTTP 与 MCP 分工

    模型选择与交接核对

    Claude Code 的模型候选来自 KiroCrew 的 provider_models.json 中 claude_code 命名空间； Kiro CLI、Codex、OpenCode 分别读取自己的命名空间，不混用模型列表。 “刷新候选”重新读取这个本机缓存，不代表实时刷新云端账号权限； 新的候选由工具在原生 ACP 会话中公布，再由 KiroCrew 更新缓存。

    当前安装的 KiroCrew 把启动模型视作继承配置：Claude ACP 拒绝一个 ID 后，可能继续使用工具默认模型。 Workflow 的明确选项有更严格的语义，因此在创建 Session、发送需求和每次 next 分派前， 检查 Claude 的明确模型是否在该工具公布的候选列表中。未公布时停止，不产生新任务。 auto / default 表示用户允许工具选择模型；未验证的可移植配置可以保存，但不能绕过本机运行前检查。

    候选列表仍不是账号权限保证。组织策略、工具自身拒绝或运行中替换模型，仍可能导致实际值变化。 运行后的核对继续严格比较模型 ID，不把 Sonnet 当成 Opus，也不因代码测试通过就放行模型不匹配。 原生任务已返回、但交接校验未通过时，界面显示“交接未通过”，与“执行失败”分开。 “调整模型并新建运行”带入原需求、打开对应 Agent 配置；用户选择支持的模型，保存新版本后再开始。 历史运行快照、检查结果与产物保持原样。

    打开 App 时的认证

    工作台中的“打开 KiroCrew”和“在 KiroCrew 中处理”均通过同一个认证入口进入原 Session。 无须手工复制 Token 或编写 MCP 配置。

    登录入口通过同源、Host 和请求头检查；从交付预览或其他站点不能调用此入口取得认证信息。 工作台不将 Token 写入工作流快照、配置、静态 HTML、自身的浏览器存储或交付报告；KiroCrew 管理自己的登录状态。 原生链接窗口最长 5 分钟，申请的浏览器 Session 生命周期为 8 小时；界面路由与认证参数由 KiroCrew 自身管理。 普通无认证的 /chat?sid=... 地址仍依赖浏览器已有的登录状态；从工作台入口打开会重新完成原生认证。

    一次运行的交互

    Session、Context 与 Memory

    一个 Workflow Run 对应一个普通 App 父 Session。 每一步 spawn_run(keep=true) 由 KiroCrew 分配独立子 Session；工具还有自己的原生 Session ID。 看板把这两种 ID 分开显示。 原生 spawn_continue 可在同一个工具会话中补齐交付，但会分配新的任务 ID。 观察器根据 App 原生续作回执关联这两个任务，核对持久化的 Conversation 归属，再验收新任务。 旧核对记录保留在 accepted/previous/；空返回 _No response._ 不能通过新核对。

    上下文通过三部分传递：用户原始输入、前面步骤的真实返回结果、同一工作目录中的文件。 完整需求和阶段指令写入 *-instructions.md，完整原生返回写入 *-result.txt， 分派文本只包含摘要与文件路径，保持在原生 spawn_run 的 5,000 字符限制内。 工作者读取完整文件，不依赖被截断的历史。首版没有跨工具共享 KV Cache， 也没有把 Claude 的原生聊天历史转换成 Codex 历史。

    本 MVP 固定 include_memory=false，因为每个任务已有明确输入，避免无关长期记忆干扰演示； KiroCrew 原有 Memory 和历史 Sessions 都保留。其他原生项目/教训上下文使用 KiroCrew 默认处理。 keep=true 也不意味着永久保活，生命周期仍受 KiroCrew 原生保留策略约束。

    Tool、Model 与 Effort 的真实边界

    选择下传方式如何核对
    ToolJSON tool → 现有模板 poc-* → ProviderRegistry → 原生 ACP Backend路由日志中的 actual_backend
    Model原生 spawn_run(model=...) → Session → Providerrequested_model 与 resolved_model
    Effort 请求原生 spawn_run(reasoning_effort=...) → reasoning_effort_overrideApp 原生工具事件中的实际请求参数
    Effort 实际值由适配器和具体模型决定仅在原生返回中确实出现时显示；缺失写“未报告”

    本机 KiroCrew 0.7.2 的 Claude/Codex 路径通过 ACP session/set_config_option 设置 Effort； 适配器可能不支持指定档位，或下降到较低档位。原生工厂接收了请求不等于模型侧一定采纳。 本机 Codex 会在部分 resolved_model 中返回 [low] 等后缀，可作为实际返回证据。 Claude 未持久化同等信息时保留“实际 Effort 未报告”，不拿模型自述证明参数生效。

    实际联调还发现两个层次的约束：Codex 裸模型 ID 在原生启动时可能被折叠到默认的 [xhigh]， 使裸模型键上的 low 覆盖失效；但公开 spawn_run 的 schema 又不允许模型 ID 含方括号。 因此转换放在已有 poc.py 的 ProviderRegistry 工厂边界：

    用户配置 / 原生 spawn_run:
  model = openai.gpt-6-astra
  reasoning_effort = low
                 ↓ 原生参数校验通过
PoC ProviderRegistry:
  model_override = openai.gpt-6-astra[low]
  reasoning_effort_override = low
                 ↓
KiroCrew 原生 ACP Client:
  model 与 reasoning_effort 分别通过 session/set_config_option 设置

    此处复用 KiroCrew 已实现的组合 ID 拆分逻辑，未修改 MCP schema 或安装包。 看板还会按该任务的真实 Codex Session ID，读取本机对应 turn_context 的 model / effort 元数据；如可用，它比仅从模型字符串后缀推断更直接。 第一次请求 low、实际 xhigh 的失败证据保留，不以“配置已发送”冒充生效。

    空 Effort 表示不添加本次覆盖，继续使用 KiroCrew 的角色/默认设置和后端默认值。 界面的“后端默认”是这一继承模式，不承诺绕过 KiroCrew 已配置的角色默认值。

    OpenCode 在当前 KiroCrew 集成中没有这条 Effort 下传路径，配置只允许后端默认。 没有把 max 当成所有工具都支持的通用值。模型下拉框是缓存候选，不是实时账号授权检查。 若实际模型与明确 pin 不一致，交接核对停止推进；观察到的 Effort 与请求不一致时也停止。

    本机 OpenCode 的 fs/write_text_file 请求与当前 KiroCrew ACP Client 不兼容，原生日志会返回 Method not found: fs/write_text_file。因此 OpenCode 阶段指令使用它已有的 Bash/Shell 工具配合 Python 或 Node 在工作目录读写文件；这条路径仍走原生工具授权。Shell 被拒绝就停止， 不增加客户自定义 RPC，不绕过权限。这不代表当前集成已经支持全部 ACP 文件操作。

    为什么这里没有直接执行 KiroCrew 原生 Workflow DSL： 本机 workflows/runner.py 接受 ctx.agent(effort=...)， 但 workflows/agent_exec.py 和 workflows/agent_pool.py 没有把它传给 SessionManager.get_or_create()。 首版使用参数链路完整的原生 spawn_run，复用此前已验证的 App/SubagentManager 方案。 原生 Workflow 的保存库、/workflow 和此处 PoC JSON 定义是不同存储，本 MVP 没有伪装成同一个原生库。

    证据与 MVP 范围

    每轮 state/runs/workflow-*/ 保存：

    • workflow-run.json：配置版本、快照与哈希。
    • input.json / workspace/REQUEST.md：用户原始需求。
    • dispatch-*.json：期望调用参数；它本身不证明任务已执行。
    • workflow-live.json / workflow-report.json：原生观察结果与参数对照。
    • accepted/*.json：真实 task-id、后端、模型、原生 Effort 请求和交接文件哈希。
    • workspace/*-handoff.md：工作者交接。
