01

先看清这个 MVP 做了什么

把它理解成一份可执行的“开发任务书”：每一项工作指定谁来做、用什么模型、交接什么结果；KiroCrew 负责把任务送到实际 Coding Agent，工作台把证据收回来。

3配置入口：文件 / Chat / Web
1–8顺序任务；不是任意 DAG
1每个 Run 对应一个 App 父对话
4候选工具；不含 Gemini

用户使用它时，真正掌握的四个选择

选择用户要表达什么系统如何处理
Task要完成什么、交付什么、怎么验证保存到步骤 prompt，运行时生成完整指令文件
Coding ToolKiro、Claude、Codex 或 OpenCode映射 Agent 模板，在 Provider factory 选择 ACP 后端
Model明确模型 ID，或允许后端自动选择传入原生请求，并区分请求与实际返回
Effort本次推理投入覆盖，或继承默认按当前工具能力校验；不保证所有模型都支持同一档位
不需要用户手写 Plan.md 和 Tasks

需求由用户输入，计划、测试和任务产物由工作者按步骤生成。工作流配置负责角色与约定，实际工程内容在运行目录中产生。

KiroCrew 原生

会话与执行底座

App Chat、托管 MCP、spawn_run、Gateway、SubagentManager、SessionManager、ACP 会话、权限与完成事件。

Octopus 扩展

配置与交接工作台

后续规划

规模化与团队能力

可靠无人值守调度、团队权限、隔离 Worker、仓库 Connector。EC2 目前只保留设计，先完成本地基础测试。

客户获得的是基于已有 KiroCrew 扩展接口交付的框架。它既不要求客户重新编写 ACP Adapter，也不能描述为“只安装未经扩展的原版 App，写一个 JSON 就自动出现这些界面”。

02

配置层决定约定，原生层负责执行

系统中有两条同时存在的路径：向下是“准备需求 → 原生分派 → 工具执行”；向上是“真实事件 → 观察与核对 → 页面显示”。进度页面的刷新不负责推进 Agent。

{{diagram:architecture}}

四个关键边界

  1. 输入边界。Web、配置文件和 Chat 最终都通过同一套结构校验、保存和版本规则。后台轮询不会替用户保存草稿。
  2. 调度边界。workflow.py next 输出精确参数。父 Agent 经原生 MCP 调用 spawn_run，而不是网页自己调用 Coding CLI。
  3. 路由边界。PocProviderRegistry.create_factory 将专用 Agent 模板映射到原生 ACP factory，保留 KiroCrew 的会话与权限流程。
  4. 证据边界。发送配置、拿到 Task ID、工具返回结果、接受交接，是不同阶段。看板必须说明每个判断来自什么证据。
ACP 和 MCP 在这里各做一件事

MCP 是父 Agent 使用 spawn_run 等工具的通道。ACP 是 KiroCrew 驱动目标 Coding Agent 会话的协议。外部 MCP Server 还可以成为目标工具可用的能力，但它不是 ACP 后端本身。

为什么不直接使用上游 Workflow DSL？

基线文档记录的本机版本中，原生 Workflow DSL 的 ctx.agent(effort=...) 没有在对应执行路径完整下传到 SessionManager。MVP 因而沿用已验证的 App → SubagentManager → spawn_run 参数链。这个选择针对当时版本，不能推导为上游永远不支持。

Octopus 的 JSON 定义、保存目录与上游原生 /workflow 库也不是同一个存储。报告会使用“Octopus Workflow”描述这里的定义，避免把两套产品能力混在一起。

文件、Chat 与 Web 如何汇合

  • 文件：JSON / YAML / Markdown 导入后先形成独立草稿；修改文件后必须执行 save 或从 Web 导入保存，没有后台文件自动监听。
  • Chat：父对话知道配置位置和版本命令，可按自然语言执行修改。网页通过“重新加载已保存配置”同步；有本地改动时明确提示将放弃当前草稿。
  • Web：向导把配置送入同一保存逻辑，不单独维护一套可绕过版本检查的定义。
冻结时刻是“准备 Run”，不一定是发送需求之后

若先创建 App 对话，再在 Chat 中修改工作流，旧对话仍属于准备时的快照。要使用新版本，需要从工作台建立一次新运行。

04

定义可以变化，本次运行的约定不能偷偷变化

Workflow 是可复用定义；revision 是一次有效保存；Run 是带有固定版本和原始需求的一次开发；每个步骤又关联一次或多次原生执行尝试。

保存时，有三道明确约束

  1. 结构校验：只接受约定字段；步骤 ID、工具、模型和 Effort 必须满足约束。
  2. 同一写入锁：文件、Web、Chat 的保存进入相同文件锁。名称经过 NFKC、空白归一和 casefold 比较，不允许不可见控制字符。
  3. 乐观版本检查：expected_revision 必须等于当前版本。冲突时要求重新加载、合并，不静默覆盖。内容没有变化时返回已有版本，不无意义递增。

版本实际文件名是零填充序号，例如 state/workflow-versions/<id>/000001.json；文档中 r1、r2 是便于阅读的简称。新 Run 保存完整定义与 SHA-256，之后通过快照核对读取。

不要把这六种 ID 混为一个 Session

身份作用是否随重试 / 新运行变化
Workflow ID一份可复用定义普通编辑不变；复制 / 导入会新建
revision定义的有效版本保存变更后增加
Run / App Session ID一次开发与父对话新运行生成时间戳 + UUID
逻辑 Task IDRun / 步骤 ID 的组合区分不同运行中的同名步骤
原生执行 Task IDspawn_run / spawn_continue 的一次执行续作产生新的执行 ID
工具 Session ID目标 Coding 工具内部会话同工具续作可能复用；跨工具不共用

名称唯一性作用于不同 Workflow ID 的当前名称，删除标记中的工作流也保留名称，避免恢复冲突。不同工作流可以都包含 code 步骤；完整身份由上层 Run / Workflow 限定。
